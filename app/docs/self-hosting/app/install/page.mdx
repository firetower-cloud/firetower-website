# Install the app

<Lede>
One command on the machine that runs the app. It checks the machine, writes the
deployment, generates the secrets and brings it up.
</Lede>

This page installs the app. Machines that run agents are a separate install
with a separate command, on [their own
page](/docs/self-hosting/machines/install).

| | The app | A machine for agents |
| --- | --- | --- |
| Command | `firetower install` | `firetower worker install` |
| Runs on | one machine — the one you open in a browser | every machine that should run agents |
| Brings up | the control plane, Postgres and Caddy | one worker container |
| Needed? | Yes | No — a new install already runs agents on itself |

## Requirements

Docker, the Compose plugin, and Node 20 or newer — on each machine you install
onto. Node comes with npm, which is what installs the CLI.

## 1. Decide where the app runs

The app is the part you open in a browser. It is not where agents run.

| | On your laptop | On a server |
| --- | --- | --- |
| Who reaches it | Only you, at `localhost` | You, over an ssh tunnel — or several people, on a name |
| Domain | Not needed | Only if more than one person uses it |
| Certificate | None | Caddy obtains and renews one, over DNS-01 |

Neither publishes the control plane to the internet. It holds every git token,
every agent credential and the root key, so the default is loopback and an ssh
tunnel — and the domain shape gets its certificate without being reachable
either. See [Put it on a domain](/docs/self-hosting/domain).

Both drive workers on other machines the same way: the app reaches out over
SSH, so those machines never need a public address.

## 2. Install the app

This is the control plane and the web interface. It does not run agents.

<Where>the machine the app will run on — your laptop, or your server</Where>

```sh
npm i -g @firetower/cli
firetower install
```

It asks four questions:

<Fields>
  <Field name="How will people reach this Firetower?">
    Three answers. **Only from this machine** publishes on `127.0.0.1` and you
    reach it with `firetower tunnel` — the default, and the one to want. **On a
    name, over HTTPS** turns Caddy on and asks which DNS provider your domain is
    behind, so it can obtain a certificate over DNS-01 without this machine
    being reachable. **Behind a reverse proxy I already run** serves plain HTTP
    on loopback for your proxy to pass through to.
  </Field>
  <Field name="Where should Firetower live?">
    A directory for the compose file, the `Caddyfile` and `.env`. Defaults to
    `~/firetower`, or `/opt/firetower` as root.
  </Field>
  <Field name="Administrator username">
    Defaults to `admin`.
  </Field>
  <Field name="Administrator password">
    Generate one, or type your own.
  </Field>
</Fields>

Before writing anything it checks the machine — Docker, the Compose plugin, the
ports it is about to publish, architecture, disk, whether `ghcr.io` is
reachable, and, when you named one, whether the domain and its wildcard resolve
to an address this machine answers on. Then it fetches the compose file from
the latest Firetower release, generates `POSTGRES_PASSWORD` and
`FIRETOWER_ROOT_KEY`, writes `.env`, shows you what it is about to do, and
brings the stack up.

With a domain it also builds Caddy with your DNS provider compiled in, which
takes a few minutes the first time.

<Output>{`  Firetower is running.

  It is on loopback, so reach it from your own machine with a tunnel:

    ssh -N -L 8080:127.0.0.1:8080 -o ServerAliveInterval=20 you@this-machine

  Then open

    http://localhost:8080

    username  admin
    password  velvet-timber-harbor-332`}</Output>

That password is printed once. You are asked to replace it when you sign in,
and then to delete `ADMIN_INITIAL_PASSWORD` from `.env`.

<Callout kind="warning">
The root key is the only unrecoverable thing here. Every stored credential is
sealed with it, and the installer makes you acknowledge it for that reason.
Back it up somewhere that is not your database backup — see
[Secrets](/docs/secrets).
</Callout>
