# Upgrade the worker

<Lede>
Firetower does it, over the same SSH connection it uses for everything else:
one machine at a time, drained first.
</Lede>

## From the Updates screen

<Where>the Firetower desktop client</Where>

**Updates** lists every machine, its worker's version, and whether it is behind
the Firetower. An upgrade run drains each machine, waits for its sessions to
end or ends them, runs the installer with the Firetower's own version, waits
for the worker to answer as that version, and puts the machine back in service.
A machine that is unreachable is skipped and named.

## From the machine's panel

**Compute → the machine → Reinstall the worker** does the same for one machine,
whenever you like. Drain it first if sessions are running: replacing the
binary does not stop a running agent, but the next session starts on the new
one.

## By hand

<Where>the machine that runs agents</Where>

```sh
curl -fsSL https://usefiretower.com/worker.sh | sh
```

installs the newest release; `--version 0.35.0` pins one. The worker keeps its
state — repositories, worktrees, the event log, the agents — under
`~/.firetower/worker`, and the installer only replaces the binary in `bin/`.

## Version drift

The Firetower compares its own version against each worker's on every connection
and says when they have drifted. `firetower upgrade` on the Firetower's own
machine also names every machine still running an older worker.

A worker that is behind still works, quietly. It runs sessions perfectly well;
what it cannot do is anything added since it was built. A worker older than the
protocol the Firetower speaks is refused at the handshake and shows as behind
until it is reinstalled. The version drift on the fleet screen is the thing to
look at when a feature seems not to exist.
