# Put it on a domain

<Lede>
By default Firetower listens on loopback and you reach it through an ssh
tunnel. Naming a domain turns on Caddy, which obtains a certificate and renews
it — **without this machine ever being reachable from the internet.**
</Lede>

That last part is the whole design. The control plane holds every git token,
every agent credential and the root key, so anyone who reaches it can erase the
codebase of the company that installed it. It does not go on the internet to
get a padlock.

## How it gets a certificate without being reachable

The usual ACME challenges — HTTP-01 and TLS-ALPN-01 — work by having Let's
Encrypt open a connection **to you**. A machine Let's Encrypt can reach is a
machine anyone can reach.

DNS-01 proves control the other way round. Caddy writes a TXT record through
your DNS provider's API, and the authority reads it back out of DNS. Every
connection Caddy makes is outbound.

<Diagram caption="Nothing connects in. The name can resolve to 10.0.0.5 and answer nobody outside your network.">{`
  +-- YOUR SERVER --------------+
  |                             |    (1) "I want *.ft.example.com"
  |   caddy  ------------------------------------------>  Let's Encrypt
  |     |                       |    (2) "prove it: TXT = abc123"
  |     | <-----------------------------------------------      |
  |     |                       |                               |
  |     | (3) write the record  |                               |
  +-----|-----------------------+                               |
        v                                                       |
   your DNS provider's API                                      |
        |                                                       |
        v                                                       |
   public DNS  <-------- (4) the authority reads the record ----+

   (5) one wildcard certificate, renewed automatically
`}</Diagram>

DNS-01 is also the only challenge that can issue a **wildcard**, which this
needs twice over: previews are served on subdomains, and one wildcard keeps
every preview hostname out of the public Certificate Transparency logs — where
a hostname that *is* the credential for that preview does not belong.

## 1. Add two DNS records

Both names, pointing at this machine. **A private address is the right answer**,
and a public one usually is not — nothing here has to be reachable from the
internet:

```
ft.example.com     A   10.0.0.5
*.ft.example.com   A   10.0.0.5
```

The wildcard is not optional. Previews are served at
`<session>-<port>-<signature>.ft.example.com`, so the bare name alone gives you
an interface that works and previews that do not resolve.

<Callout kind="warning">
There is nothing to open in a firewall. Port 80 is published only to redirect
to 443, and no challenge is answered on it — drop it if you would rather
nothing answered there at all.
</Callout>

## 2. Give Firetower the domain

On a fresh install `firetower install` asks these questions as part of the
install. On one that is already running:

```sh
firetower domain ft.example.com
```

Or with no argument at all, to be asked everything:

```sh
firetower domain
```

### What it asks, and what it answers

It opens with what the deployment is today, so you can see what you are
changing:

<Output>{`  Firetower

  deployment    /opt/firetower
  reached by    this machine only, over an ssh tunnel`}</Output>

Then the reach question. `●` is the current selection; arrow keys move it:

<Output>{`  ◆  How will people reach this Firetower?
  │  ○ Only from this machine, over an ssh tunnel  (recommended)
  │  ● On a name, over HTTPS
  │  ○ Behind a reverse proxy I already run
  └`}</Output>

<Output>{`  ◇  Domain
  │  ft.example.com`}</Output>

**As soon as it has the name it prints the records**, before asking anything
else and long before anything is written — with this machine's own address
filled in, because the right answer being a *private* address is the part
people do not expect:

<Output>{`  Both of these have to exist, pointing at this machine:

    ft.example.com      A   10.0.0.5
    *.ft.example.com    A   10.0.0.5

  The wildcard is not optional — previews are served on subdomains.
  A private address is the right answer here, and a public one usually
  is not: nothing about this has to be reachable from the internet.`}</Output>

Then where the certificate comes from. The ten providers that need a single API
token are listed; anything else is typed, and the last answer is for a
certificate you already hold:

<Output>{`  ◆  Where should the certificate come from?
  │  ● Let's Encrypt, through Cloudflare
  │  ○ Let's Encrypt, through DigitalOcean
  │  ○ Let's Encrypt, through Hetzner
  │  ○ Let's Encrypt, through Vercel
  │  ○ Let's Encrypt, through GoDaddy
  │  ○ Let's Encrypt, through deSEC
  │  ○ Let's Encrypt, through Gandi
  │  ○ Let's Encrypt, through Linode
  │  ○ Let's Encrypt, through Vultr
  │  ○ Let's Encrypt, through DuckDNS
  │  ○ Let's Encrypt, through another DNS provider…
  │  ○ I already have a certificate
  └`}</Output>

The token is masked as you type, and never printed back:

<Output>{`  ◇  API token for cloudflare
  │  ▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪`}</Output>

It then checks DNS itself — including a random label under the domain, which is
the only way to tell a wildcard record from a single one that happens to exist:

<Output>{`  Checking DNS
  ✗ domain  ft.example.com does not resolve
    point an A record at this machine — the address browsers reach it on, which on a private network is a private one`}</Output>

And finally the plan, with every `.env` change named — **the token masked
here too**, because this block is what people paste into an issue:

<Output>{`  Here is what I will do:

  reached by    ft.example.com, over HTTPS
  published     127.0.0.1:8080 — and Caddy on 443 and 80, for everyone else
  certificate   Let's Encrypt, over DNS-01 through cloudflare — renewed by Caddy
  url           https://ft.example.com

  .env:

    COMPOSE_PROFILES         unset → tls
    DNS_API_TOKEN            unset → ••••••••
    DNS_PROVIDER             unset → cloudflare
    DOMAIN                   empty → ft.example.com
    FIRETOWER_PREVIEW_DOMAIN unset → ft.example.com
    FIRETOWER_PUBLIC_URL     http://localhost:8080 → https://ft.example.com
    HTTPS_PORT               unset → 443

  ◆  Continue?
  │  ● Yes / ○ No`}</Output>

Answering **No** writes nothing. Nothing about the release moves either way: no
images are pulled, no migrations run, no database is touched.

### Without the prompts

Every answer has a flag, for a scripted install:

```sh
firetower domain ft.example.com \
  --dns-provider cloudflare --dns-token "$CLOUDFLARE_TOKEN"
```

`--dns-token` on its own rotates the credential and keeps the rest.
`--dns-provider` on its own moves zones. `firetower domain --none` takes the
domain away again and puts the deployment back on loopback — removing the Caddy
container with it, which a plain `docker compose up -d` would not.

## 3. Wait for the first build, then the certificate

Caddy resolves DNS providers as **compiled-in modules**, so the first start
builds a Caddy with yours in it. That takes a few minutes rather than seconds,
once — it is cached afterwards — and it needs a reachable Go module proxy at
that moment.

```sh
firetower logs caddy -f
```

Then `firetower doctor` reports what it can see:

<Output>{`  ✓ domain               ft.example.com → 10.0.0.5, an address on this machine, and *.ft.example.com resolves
  ✓ certificate          Caddy renews it, over DNS-01 through cloudflare — none issued yet`}</Output>

Renewal is Caddy's, unattended, at about two-thirds of the certificate's life.
There is nothing for you to run.

## Which providers

Every module under [github.com/caddy-dns](https://github.com/caddy-dns) — all
ninety-six — and the CLI knows their names. **Each one, and what its credential
is, is on [DNS providers](/docs/self-hosting/domain/providers).** It rejects a
name that is not one of them, and suggests the closest:

<Output>{`  $ firetower domain ft.example.com --dns-provider cloudflares
  error: no caddy-dns module called cloudflares — did you mean cloudflare?`}</Output>

That check earns its keep because the name is compiled in: an unchecked typo
fails several minutes into a Go build, not at start-up.

**One API token.** Cloudflare, DigitalOcean, Hetzner, Vercel, GoDaddy, deSEC,
Gandi, Linode, Vultr and DuckDNS are offered by name and need nothing else.
GoDaddy's token is its key and secret joined by a colon — `KEY:SECRET` — which
the prompt says, because pasting the key alone fails only at issuance.

**Several values.** Route 53, Azure, Google Cloud, Namecheap, Porkbun, OVH and
about forty others cannot be expressed by a single token. Choose them anyway —
the right module is built in, and Firetower writes their block into the
`Caddyfile` for you to fill in:

```
tls {
	dns {$DNS_PROVIDER} {
		# route53 takes more than one value, so it cannot use the
		# one-line form. Its settings go here:
		#
		#     https://github.com/caddy-dns/route53
	}
}
```

An empty block is a real configuration for several of them — the AWS, Azure and
Google SDKs read their own environment variables, which you add to the `caddy`
service in `firetower.yml`. `firetower upgrade` rewrites `firetower.yml` and
never touches the `Caddyfile`, so your edit survives.

## If it doesn't work

| In `firetower logs caddy` | What it means |
| --- | --- |
| `module not registered: dns.providers.x` | `DNS_PROVIDER` changed without a rebuild — `firetower domain` again, or `up -d --build` |
| `wrong argument count ... {env.DNS_API_TOKEN}` | That provider takes several values; its block needs writing in the `Caddyfile` |
| `401`, `403`, `authentication failed` | `DNS_API_TOKEN` is wrong, or scoped to the wrong zone |
| `no such host` on the challenge | The record is not there yet — propagation is minutes |
| `too many certificates already issued` | Rate limit. Five duplicate certificates a week; keep the `caddy_data` volume across restarts |
| `go: module ... not found` during the build | The provider module or one of its dependencies will not compile — see below |

To get warned before a renewal that has started failing, set `ACME_EMAIL` in
`.env`, or pass `--acme-email you@example.com` to `firetower install`.

<Callout kind="warning">
Building from source means a provider module can be held back by something it
depends on rather than by anything in it — `caddy-dns/vercel` is, today, and
Firetower applies the fix for you. If you hit one it does not know about, set
`DNS_MODULE_REPLACE=old=new@version` in `.env`; it is passed to
`xcaddy --replace`. Delete it once the module's maintainer tags a release.
</Callout>

## Bringing your own certificate

For a corporate CA, a provider with no Caddy module, or a machine that cannot
reach a Go module proxy. Answer **"I already have a certificate"**, or install
with `--domain` and no `--dns-provider`:

```sh
firetower install --domain ft.example.com
```

Put `fullchain.pem` and `privkey.pem` in `certs/` beside `firetower.yml`,
covering both the name and `*.the-name`, and uncomment the `tls` line in the
`Caddyfile`. Renewal is yours again, and `firetower doctor` warns when there
are under three weeks left.
