# How self-hosting works

<Lede>
You run two things: **the app**, once, and **a worker** on every machine that
should run agents.
</Lede>

The app reaches your machines over SSH. The worker never opens a port and
holds no credentials of its own.

### The app

Three containers, brought up by `firetower install`:

- **firetower** — the control plane and the web interface, compiled into one
  binary. It decides what should happen, holds your hosts, repositories and
  credentials, and serves the screen you work in.
- **postgres** — the entire state, with every credential sealed. See
  [Secrets](/docs/secrets).
- **caddy** — TLS, and only TLS. It is behind a compose profile and is **not
  created** unless you name a domain: with no certificate to terminate it would
  be a pass-through in front of a server that already serves its own interface,
  API and preview routing.

The control plane publishes `127.0.0.1:8080` — loopback, deliberately. It holds
every git token, every agent credential and the root key, and a host firewall
would not close a published port anyway, because Docker writes its own DNAT
rules and they are consulted before the host's `INPUT` chain. You reach it with
`firetower tunnel`, or you name a domain and Caddy terminates TLS in front of
it — obtaining the certificate over DNS-01, so even then nothing has to be
reachable from the internet.

### The worker

One container per machine, `firetower-worker`, holding what a session needs:
git, tmux and the agents themselves.

It does nothing on its own — Firetower SSHes to the
machine and runs `docker exec` when it wants to talk. No sshd in the image, no
key inside it, no port to open.

Each worker writes what happened to its own event log before reporting it, so a
session survives the app being unreachable.

<Callout>
The machine running the app is also a host. The control plane starts a worker
as a child process, so `localhost` appears in the fleet, runs sessions, and can
be drained.
</Callout>

## What you actually have to do

1. **Run the app.** One command on any machine that can reach the internet.
   → [Install](/docs/self-hosting/app/install)
2. **Give it a name**, if more than one person uses it and a tunnel each is not
   reasonable. → [Custom domain + Tailscale](/docs/self-hosting/app/install/server-with-custom-domain)
3. **Run a worker** on every machine that should run agents, and add each one
   in Compute. → [Add a machine](/docs/self-hosting/machines/install)

Step 3 is optional. A new install already has one host — itself — and runs
sessions there.

## Shapes that work

| Where the app runs | Where workers run | Good for |
| --- | --- | --- |
| One machine | The same machine | Trying it, and small teams. Nothing else to set up. |
| A small VPS | Bigger machines you add over SSH | Keeping the thing you expose small and cheap, and the compute separate. |
| Your laptop | Cloud VMs | Working locally while the agents run somewhere that stays awake. |

The work happens on the workers. Size those; the app only holds state and
serves the interface.

<Callout kind="warning">
Back the root key up separately from the database. A database backup on its
own cannot be decrypted; stored beside the key, it can.
</Callout>
